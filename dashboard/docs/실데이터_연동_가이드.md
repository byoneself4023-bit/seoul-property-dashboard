# 실데이터 연동 가이드 (국토부 실거래가 → 대시보드)

거래량 대시보드를 **목데이터 → 실데이터**로 전환하는 절차. 데이터 출처는 국토교통부 실거래가(RTMS) 공개 API(공공데이터포털, data.go.kr)이며, **매매**만 집계한다.

- **아파트** = 아파트 매매
- **비아파트** = 연립다세대 + 단독/다가구 + 오피스텔(준주택). 국토부 주택거래량 통계와 대조 시 오피스텔만큼 차이 발생할 수 있다.

배포 없이 "파일 열기" 모델을 유지하기 위해, 인제스트 스크립트(`ingest.mjs`)가 API를 호출·집계해 결과 JSON을 **`dashboard.html` 안에 인라인**한다. 브라우저는 `file://`에서 외부 JSON을 `fetch`하지 못하므로(로컬 CORS 차단) 인라인 방식이 필수다. API 키는 로컬 `.env`에만 두고, 공유하는 HTML에는 집계 결과만 들어간다.

---

## 1. API 인증키 발급 (사용자 작업 — 1회)

RTMS 실거래가 API는 무료지만 공공데이터포털 가입 + 활용신청이 필요하다.

1. **data.go.kr 가입/로그인** — https://www.data.go.kr
2. **매매 API 4종 각각 "활용신청"** (자동승인, 즉시 발급):
   - 국토교통부_아파트 매매 실거래가 상세 자료 — https://www.data.go.kr/data/15126468/openapi.do
   - 국토교통부_연립다세대 매매 실거래가 자료 — https://www.data.go.kr/data/15126467/openapi.do
   - 국토교통부_단독/다가구 매매 실거래가 자료 — data.go.kr에서 "단독다가구 매매 실거래가"로 검색 후 활용신청
   - 국토교통부_오피스텔 매매 실거래가 자료 — data.go.kr에서 "오피스텔 매매 실거래가"(`RTMSDataSvcOffiTrade`)로 검색 후 활용신청 (**별도 신청 필요**; 미신청 시 오피스텔 유형만 건너뛰고 나머지 3종은 정상 수집됨)
   - (네 API 모두 같은 서비스키를 공유한다. 한 계정의 인증키로 4개 API를 모두 호출한다.)
3. **인증키 확인** — 마이페이지 > 오픈API > 인증키. **일반 인증키(Decoding)** 값을 복사한다.
   - 인코딩/디코딩 키가 따로 표시되면 **Decoding 키**를 쓴다(스크립트가 URL 인코딩을 직접 처리).

## 2. 로컬 설정

프로젝트 루트에 `.env` 생성(이미 `.gitignore`에 포함 — 커밋되지 않음):

```
RTMS_SERVICE_KEY=여기에_디코딩_인증키_붙여넣기
```

## 3. 실행

```bash
node dashboard/ingest.mjs           # 일반 실행 (캐시 활용)
node dashboard/ingest.mjs --fresh   # 캐시 무시, 전체 재수집
```

- 25개 구 × 최근 13개월 × 매매 4종 = **최대 1,300건** API 호출.
  공공데이터포털 일반 개발 계정의 일일 호출 한도는 **10,000건**이므로 하루 안에 여유 있게 완료된다.
- **캐시 동작**: 각 응답은 `dashboard/.cache/ingest/` 에 `(LAWD_CD)_(DEAL_YMD)_(propertyType).json` 형태로 저장된다.
  재실행 시 이미 캐시된 콤보는 네트워크 호출 없이 로컬 파일을 읽는다.
  실행 도중 오류(네트워크 장애, 한도 초과 등)로 중단된 경우에도 **이미 수집된 분은 보존**되므로,
  `node dashboard/ingest.mjs` 를 다시 실행하면 **실패한 콤보만 재시도**한다.
- **최근 2개월 자동 재수집**: 직전월+당월(예: 202606, 202607)은 신고가 계속 들어오므로 **캐시가 있어도 자동으로 무시하고 재수집**한다(약 25구×2개월×4종=200회 추가, 한도 대비 무시 가능). 따라서 **매월 초 `node dashboard/ingest.mjs`만 재실행하면 직전월이 확정치로 갱신**된다. 과거 확정월(11개월)은 캐시로 건너뛴다.
- **`--fresh` 플래그**: 캐시를 완전히 무시하고 모든 콤보(1,300회)를 재수집한다. 데이터를 처음부터 다시 받고 싶을 때만 사용.
- **캐시 스키마 버전(v2)**: 캐시 파일에는 `schemaVersion` 필드가 있고, 로드 시 `schemaVersion === 2` 인 캐시만 히트로 인정한다. 전용면적·거래금액이 없던 구버전(v1, 날짜만 저장) 캐시는 **자동으로 미스 처리되어 재수집**되므로, 필드 추가 후에는 `--fresh` 없이 `node dashboard/ingest.mjs` 만 실행해도 전체가 v2로 갱신된다(첫 v2 전환은 1,300회 전량 재수집).
- **일일 한도 초과** 시 스크립트는 즉시 멈추고 "일일 한도 초과 — 내일 재실행(캐시로 이어서 진행됨)" 메시지를 출력한다.
  다음 날 `node dashboard/ingest.mjs` 를 재실행하면 캐시가 있는 콤보를 건너뛰고 나머지만 수집한다.
- 완료 후 `dashboard.html`을 열면 배지가 **"목데이터" → "실데이터"** 로 바뀌고, 헤더에 **"데이터 수집일: YYYY-MM-DD"**(인제스트 실행일)가 표시된다.
- 집계 규칙: 월간 = 계약년월 기준 최근 12개 완결 월, 주간 = 계약일 기준 월~일 최근 12개 완결 주. 각 기간·구별로 아파트/비아파트 **건수**에 더해, **공간규격 버킷**(전용면적, 아파트+연립+오피스텔)과 **금액대 버킷**(거래금액, 비아파트만)을 함께 집계해 대시보드의 3모드 차트(거래추이·공간규격별·금액대별)에 사용한다.

## 4. 주의 — 신고 지연

실거래가는 계약 후 신고까지 시차(최대 30일)가 있어 **가장 최근 기간은 과소 집계**될 수 있다. 대시보드 기본값이 "완결 기간"이라 진행 중 기간은 이미 제외되지만, 최신 완결월도 신고가 진행 중이면 낮게 보일 수 있다.

- 실측 사례: 수집 시점(2026-07-10) 기준 2026-06 아파트가 2026-05 대비 낮게 나타남 — 6월 신고분이 계속 유입 중이기 때문. 최근 2개월은 재실행 시 자동 갱신(위 §3)되므로, **매월 초 재실행하면 직전월이 확정치로 보정**된다.

## 5. 주간 자동 갱신 (launchd — 이 맥 한정)

쿠카 맥에서 **매주 월요일 07:00** 에 `dashboard/ingest.mjs` 를 자동 실행해, dashboard.html 을 열면 항상 최신 스냅샷이 되게 한다. 서버·배포 없이 이 맥 로컬 자동화(launchd 사용자 LaunchAgent).

### 등록 / 해제 / 즉시 실행

```bash
# 등록(재등록 안전 — 시각 변경 후 재실행하면 갱신):
sh dashboard/scripts/install-scheduler.sh
# 해제:
sh dashboard/scripts/uninstall-scheduler.sh
# 즉시 1회 실행(검증용, 스케줄 안 기다림):
launchctl kickstart -k gui/$(id -u)/com.kuka.dashboard-ingest
# 상태/실행횟수/마지막 종료코드:
launchctl print gui/$(id -u)/com.kuka.dashboard-ingest
```

**시각 변경**: `dashboard/scripts/install-scheduler.sh` 상단 `START_WEEKDAY`(0/7=일, 1=월 … 6=토) · `START_HOUR` · `START_MINUTE` 수정 후 재실행.

### 동작 / 로그

- 실행 내용: `node dashboard/ingest.mjs` — 최근 2개월(직전월+당월)만 재수집(~200회), 나머지는 캐시 히트(0 호출). 완료 시 `data.json` + dashboard.html `#real-data` 슬롯의 `generatedAt`(= "데이터 수집일")이 실행일로 갱신된다.
- node 는 절대경로 사용(launchd 는 PATH 가 최소). 설치 시 `which node` 결과를 plist `EnvironmentVariables`(INGEST_NODE)로 주입한다.
- 로그: `dashboard/logs/ingest-launchd.log` — 매 실행 새로 쓰고(덮어쓰기), 직전 실행분만 `.log.prev` 로 1세대 보관(무한 증식 방지). launchd 레벨 오류는 `dashboard/logs/launchd-stderr.log`. (두 파일 모두 `logs/` 규칙으로 git 미추적)

### 놓친 스케줄 보정 — 실제 보장 범위 (과장 없이)

- **잠자기(sleep) 중** 07:00 을 지나침 → 맥이 **깨어날 때 1회 실행**된다(launchd `StartCalendarInterval` 의 표준 동작, 여러 번 놓쳐도 1회로 합쳐짐). ✅
- **완전 종료(shutdown) 상태**로 07:00 을 지나침 → launchd 는 이 경우를 **소급 실행하지 않는다**. 다음 월요일 07:00 까지 대기한다. ❌ (launchd 한계 — 보장 안 됨)
- 즉, 평소 닫아두거나 잠자기면 자동 보정되지만, 월요일 아침 내내 전원을 꺼두면 그 주는 건너뛴다. 그럴 땐 위 `launchctl kickstart` 로 수동 1회 실행하면 된다.

### 실패 안전

`ingest.mjs` 의 dashboard.html 주입(`inject`)은 **수집·집계가 성공한 뒤에만** 일어난다. 네트워크 장애·API 한도 등으로 수집이 중단되면 주입 전에 종료(exit 1)되므로 **기존 dashboard.html 은 직전 스냅샷 그대로 유효**하다. 부분 실패(일부 콤보만 실패)여도 캐시 기반 최선값으로 정상 스냅샷을 유지한다.

### 한계

- 이 맥에서만 자동 갱신된다. 남에게 **전달한 dashboard.html 은 전달 시점의 스냅샷**이며 자동으로 갱신되지 않는다(인라인 데이터 단일 파일 모델).
- 공유·배포까지 자동화하려면 후속으로 **GitHub Actions cron**(주 1회 ingest → 커밋) 또는 **서버리스 함수 + cron**(Vercel/Supabase)로 승격한다(배포 전제).

## 6. 병렬 작업 폴더 구조 (git worktree)

대시보드와 뉴스레터를 브랜치 전환·stash 없이 상시 병렬로 작업하기 위해 저장소 하나를 두 작업 폴더로 나눈다(git worktree — 커밋 이력·크로스 의존은 그대로 공유).

| 폴더 | 상주 브랜치 | 용도 |
|------|-----------|------|
| `~/Project` | `feature/SPEC-NEWSLETTER-002` | **뉴스레터 전용** (진행 중 WIP 상주) |
| `~/Project-dash` | `main` | **대시보드 전용** (제품 홈) |

- [규칙] **대시보드 수정은 `~/Project-dash` 에서** 한다(main 커밋). 뉴스레터 수정은 `~/Project` 에서 한다.
- launchd 주간 자동 갱신(§5)은 대시보드 홈인 `~/Project-dash` 기준으로 동작한다(plist 가 `~/Project-dash/dashboard/scripts/run-ingest.sh` 를 가리킴). 시각·등록 변경도 `~/Project-dash` 에서 `install-scheduler.sh` 재실행.
- **공유 자원(심볼릭 링크)**: `git worktree add` 는 gitignore 대상을 복제하지 않으므로, `~/Project-dash` 에서 아래 3개를 `~/Project` 로 심볼릭 링크해 공유한다(재수집·재설치·키중복 방지):
  - `dashboard/.cache` → 캐시 공유. **없으면 신규 폴더에서 5,500여 콤보 전량 재수집**. 공유 시 ingest 는 최근 2개월(~200회)만 재수집한다.
  - `.env` → RTMS 인증키 공유 (키 복제·노출 없음).
  - `node_modules` → puppeteer 등 개발 의존성 공유 (verify-quality 실행용).

  ```bash
  ln -s ~/Project/dashboard/.cache ~/Project-dash/dashboard/.cache
  ln -s ~/Project/.env             ~/Project-dash/.env
  ln -s ~/Project/node_modules     ~/Project-dash/node_modules
  ```
- **worktree 제거**: `git worktree remove ~/Project-dash` (심볼릭 링크는 원본 `~/Project` 자원을 지우지 않는다).
- **참고 — data.json 분리**: 각 worktree 는 자기 `dashboard/data.json` 을 가진다. 자동 갱신은 `~/Project-dash/dashboard/data.json` 을 최신화하지만, 뉴스레터(`~/Project`)가 읽는 `~/Project/dashboard/data.json` 은 별개다 — 뉴스레터 거래량 스냅샷을 최신으로 쓰려면 뉴스레터 쪽 참조 경로를 `~/Project-dash` 로 두거나 별도 갱신이 필요하다(후속 결정).

## 부록: API 스펙 (스크립트 구현 근거)

- 엔드포인트(provider `1613000`, 4종 모두 동일한 파라미터·응답 구조):
  - 아파트 매매: `http://apis.data.go.kr/1613000/RTMSDataSvcAptTradeDev/getRTMSDataSvcAptTradeDev`
  - 연립다세대 매매: `http://apis.data.go.kr/1613000/RTMSDataSvcRHTrade/getRTMSDataSvcRHTrade`
  - 단독/다가구 매매: `http://apis.data.go.kr/1613000/RTMSDataSvcSHTrade/getRTMSDataSvcSHTrade`
  - 오피스텔 매매: `http://apis.data.go.kr/1613000/RTMSDataSvcOffiTrade/getRTMSDataSvcOffiTrade` (**별도 활용신청 필요**)
- 요청 파라미터: `serviceKey`, `LAWD_CD`(5자리 시군구 법정동코드), `DEAL_YMD`(YYYYMM), `pageNo`, `numOfRows`
- 응답: XML `<item>` 반복. 집계에 사용하는 필드:
  - `<dealYear>`/`<dealMonth>`/`<dealDay>`(구형 한글 태그: `<년>`/`<월>`/`<일>`) — 월간·주간 버킷팅(구는 LAWD_CD로 이미 확정).
  - `<excluUseAr>`(전용면적 m²) — **공간규격별 차트**용. 원룸형 ≤40 / 투룸형 40~60 / 쓰리룸+ >60(경계값은 `ingest.mjs` 상단 `AREA_BUCKETS` 상수). **단독/다가구(SH)는 전용면적 필드가 없고 대지면적(`plottageAr`)·연면적(`totalFloorAr`)만 제공하므로 공간규격 집계에서 제외**된다(SH는 금액대 집계에는 정상 포함).
  - `<dealAmount>`(거래금액 만원, 쉼표 포함 문자열) — **금액대별(비아파트) 차트**용. 3억↓ / 3~6억 / 6억↑(경계값은 상단 `PRICE_BUCKETS` 상수). 아파트는 금액대 차트에서 제외(라벨이 "금액대별(비아파트)").
  - **건수 = 응답의 `<totalCount>` 필드** (개별 `<item>` 개수가 아님). `totalCount > numOfRows` 이면 `pageNo` 를 증가시켜 전체 페이지를 수집한다.
