### verify-gate.sh (Stop) — 검증 게이트

변경된 파일을 보고 필요한 검증만 돌린다.

| 바뀐 파일 | 도는 검증 |
|---|---|
| `dashboard/ingest.mjs` | `node --check` + `node dashboard/ingest.mjs --selftest` |
| `dashboard.html` / `data.js` / `verify-quality.mjs` | `npm run verify` |
| `dashboard/scripts/*.sh` | `sh -n` (전체 스크립트) |
| (항상) | 추적 파일 삭제 여부, gitignore 대상이 스테이징에 들어왔는지 |

`npm run verify` 는 puppeteer로 실제 브라우저를 띄우므로 화면·데이터가 바뀐
경우에만 돈다. 매번 돌리면 느려서 게이트를 끄고 싶어진다.

실패하면 `{"decision":"block"}` 을 내어 정지를 되돌리고 계속 작업하게 한다.
**재시도 3회 상한.** 상한에 걸리면 block 대신 `systemMessage` 로 멈추고,
몇 번 시도했고 무엇이 실패했는지 남긴다. 상태는 `.claude/.state/` (gitignored).

### guard-destructive.sh (PreToolUse) — 되돌릴 수 없는 작업 가드

| 대상 | 판정 |
|---|---|
| `.cache/ingest` 삭제 | **deny** — 이 맥에만 있는 원본 45만 건, 재수집 5,500회 |
| force push | **deny** — 원격 이력 파괴 |
| `rm` / `rmdir` 일반 | ask |
| `git reset --hard`, `git clean -f`, `filter-branch/repo` | ask |
| 핵심 파일에 `>` 리다이렉트, `cp`/`mv` | ask |
| `deploy.sh`, `run-ingest.sh`, `ingest.mjs`(selftest 아님) | ask |
| 산출물 파일 Write 전체 덮어쓰기 | ask |

`npm run verify`, `--selftest`, 일반 push, 새 파일 Write 는 조용히 통과한다.

### block-secrets.sh (PreToolUse) — 비밀값 차단

- `.env` 의 실제 값과 대조. **차단 사유에는 변수 이름만 적고 값은 절대 출력하지 않는다**
- 키 형태 탐지 — Anthropic 키, GitHub 토큰, 키에 리터럴 값 대입
- Bash 전용 — `.env` 스테이징, 전체 스테이징 명령, `.env` 를 파이프/리다이렉트로
  내보내는 조합, 키 값 echo

**알려진 한계.** 훅은 Bash 명령 문자열 전체를 스캔하므로 heredoc 본문에 차단
패턴을 *문자열로* 적으면 오탐이 난다. 실제로 두 번 겪었다 — 커밋 메시지에 전체
스테이징 명령을 설명으로 적었을 때, 그리고 이 문서에 `.env` 를 읽는 예시 명령을
적었을 때. 전자는 메시지를 파일로 분리해 `git commit -F` 로, 후자는 Bash heredoc
대신 파일 쓰기 도구로 우회했다. 안전한 방향의 오탐이라 규칙을 느슨하게 하지
않고 그대로 뒀다.

### 4-2. 발행·감시 워크플로 (완료)

**`.github/workflows/pages.yml`** — `main` 에 화면·데이터가 푸시되면 두 파일만
`_site/` 로 조립해 Pages 로 올린다. 저장소 전체가 서빙되지 않는다.

- `dashboard.html` → `index.html` 개명은 여기서 한다. 저장소의 파일명을 바꾸면
  `ingest.mjs` 의 `inject()` 가 깨지므로 원본은 그대로 둔다
- 발행 전 점검 — 두 파일이 비지 않았는지, `index.html` 에 `data.js` 참조가 있는지,
  `data.js` 에 전역 할당이 있는지. 하나만 올라가 목데이터로 뜨는 것을 막는다
- `paths` 필터로 문서만 고친 커밋은 배포를 트리거하지 않는다
- `concurrency: pages`, `cancel-in-progress: false` — 반쯤 올라간 상태를 만들지 않는다

**`.github/workflows/freshness.yml`** — 이번 전환의 핵심.

4주간 라이브가 멈춘 걸 아무도 몰랐던 이유는 알림 부재가 아니라 **돌지 않은 작업은
실패하지도 않는다**는 데 있다. 수집이 죽으면 실패 알림도 안 온다. 그래서 수집과
독립된 감시를 둔다.

- 매일 09:00 KST, 라이브의 `data.js` 에서 `generatedAt` 을 읽어 **10일** 넘으면 실패
- 화면·데이터 각각 HTTP 200 도 확인 — `data.js` 만 404 면 목데이터로 뜬다
- 실패하면 **이슈를 자동 생성**한다. 메일은 묻히지만 이슈는 저장소를 열면 보인다.
  열린 이슈가 있으면 중복 생성하지 않는다
- 공개 저장소는 60일 무활동 시 스케줄이 자동 비활성화된다. 이 감시가 매일 돌면
  그 전에 사람이 알아챈다

두 워크플로 모두 `workflow_dispatch` 를 열어뒀다.

**메일 알림 설정** (1회, 웹) — GitHub Settings → Notifications → Actions →
드롭다운을 **"Only notify for failed workflows"** 로. 스케줄 워크플로의 알림은
그 워크플로를 만든 사용자에게 간다.

### 4-3. `deploy.sh` 축소 (완료)

자기 저장소 발행이라 114줄 → **89줄**. `gh` 의존이 통째로 사라졌다.

걷어낸 것 — 배포 저장소 clone/fetch/reset, `gh auth setup-git`, 배포 저장소로의
별도 commit/push, Pages 빌드 상태 폴링, `OWNER`/`REPO` 상수.

남긴 것 — `generatedAt` 추출, no-op 스킵(빈 커밋 방지), **두 파일을 항상 함께
다루는 규칙**, 그리고 **라이브 검증**(화면·데이터 각각 HTTP 200 + sha256 일치).
라이브 검증이 가장 중요하다. Pages 로 남는다고 4주 침묵의 위험이 사라지지 않는다.

라이브 주소는 `origin` 에서 유도한다 — 저장소 이름이 바뀌어도 따라간다.
`sed -E` 의 lazy 수량자가 BSD(macOS)에서 안 되므로 파라미터 확장만 썼다.

`run-ingest.sh` 는 그대로다. 수집 성공(rc=0)일 때만 배포하는 구조가 유효하다.

> **앞으로 없어질 수 있다.** 수집을 GitHub Actions 로 옮기면(`.cache` 133MB 설계가
> 정해진 뒤) 워크플로가 수집·커밋·푸시를 모두 하므로 `deploy.sh` 와 `run-ingest.sh`
> 둘 다 사라진다. 지금 축소한 것은 그때까지의 다리다.

### 4-4. 에이전트 워크플로 (완료)

이슈·PR 코멘트에 `@claude` 를 언급하면 에이전트가 조사·구현해 브랜치를 올리고
Draft PR 이 열린다. 인증은 `ANTHROPIC_API_KEY` 시크릿(콘솔 API 키)이다.
구독 OAuth 토큰(`sk-ant-oat…`)은 쓰지 않는다 — `anthropic_api_key` 입력에 넣으면
`Invalid API key` 로 거부된다.

| 파일 | 역할 |
|---|---|
| `claude.yml` | `@claude` 트리거. 에이전트 실행 후 브랜치 확인 → 품질 게이트 → Draft PR |
| `verify.yml` | 사람이 여는 PR과 수동 실행용 품질 게이트 |
| `auto-pr.yml` | 백스톱. 사람이 `claude/**` 를 push 하거나 수동 실행할 때 |
| `.github/scripts/open-draft-pr.sh` | PR 생성 로직 (두 워크플로가 공유) |
| `.github/claude-ci-settings.json` | CI 전용 permissions + 훅 3개 |

**러너 환경에서 실제로 걸린 것 두 개.** 문서로는 안 보이고 돌려봐야 나왔다.

- `puppeteer` 25 의 `executablePath()` 가 **Promise 를 반환**한다. `await` 없이
  `test -x` 에 넣어 항상 실패했다 — 환경 문제가 아니라 검사 코드 오류였다
- **Ubuntu 23.10+ 가 AppArmor 로 비특권 user namespace 를 막아** 크롬 샌드박스가
  뜨지 못했다(`No usable sandbox`). `verify-quality.mjs` 에 `--no-sandbox` 를 넣는
  대신 러너 쪽 제한(`kernel.apparmor_restrict_unprivileged_userns=0`)을 풀었다.
  로컬(macOS)과 CI 가 같은 조건에서 같은 게이트를 돌아야 게이트가 의미를 갖는다

**CI 에는 물어볼 사람이 없다.** 로컬 `settings.json` 의 `ask` 규칙이 CI 에서는 곧
거부가 되고, 그 거부가 재시도 루프를 만든다. 실제로 에이전트가 `gh api -X PATCH` 로
코멘트를 갱신하려다 8번 막히며 20턴을 소진하고 죽었다. `claude-ci-settings.json` 을
분리해 `ask` 를 0개로 두고 필요한 것만 allow, 위험한 것은 deny 로 못박았다.
**훅 3개는 로컬과 바이트 단위로 동일하게 싣는다** — 방어선은 그대로다.

**에이전트의 도구 선택은 신뢰하지 않는다.** 허용된 `mcp__github_comment__update_claude_comment`
를 두고 `gh api` 로만 8번 시도한 전례가 있다. 그래서 PR 생성·검증을 프롬프트로
지시하지 않고 **셸 단계**로 처리한다.

**에이전트가 실패해도 뒤 단계는 돈다.** 턴 소진으로 죽어도 커밋·푸시는 이미 끝났을
수 있으므로 `if: ${{ !cancelled() }}` 를 쓴다. 단 브랜치가 없으면 `found=false` 로
걸러져 PR 이 만들어지지 않는다. 품질 게이트에는 `continue-on-error` 를 걸어
게이트 실패가 PR 생성을 막지 않게 했다 — 실패한 채로 보이는 편이 침묵보다 낫다.

**PR 은 액션이 만들지 않는다.** `claude-code-action` 은 설계상 브랜치만 올리고
"Create PR" 링크를 남긴다(FAQ: 브랜치 보호 준수와 사람의 최종 판단). 그래서
PR 생성을 우리가 한다. 중복은 **브랜치 단위 + 이슈 단위** 두 겹으로 막는다 —
같은 이슈의 열린 PR 이 있으면 만들지 않고 기존 PR 에 새 브랜치를 알린다.

**막혔던 설정 두 개**

- `Actions is not permitted to create or approve pull requests` →
  `can_approve_pull_request_reviews: true` 로 변경. 이 체크박스는 생성과 승인을
  함께 허용하는데, 아래 브랜치 보호에서 승인을 요구하지 않으므로 무해하다
- 에이전트의 push 는 **`github-actions[bot]`(id 41898282)** 이름으로 나간다.
  진짜 `claude[bot]`(id 209825114) 이 아니다. GitHub 은 이 봇이 만든 이벤트로
  워크플로를 트리거하지 않으므로 **브랜치 push 에 반응하는 워크플로는 영영
  돌지 않는다.** 그래서 검증·PR 생성을 에이전트와 같은 잡으로 옮겼다

### 4-5. 공개 전환 + Pages (완료)

공개 직전 이력 전체를 다시 훑어 키 패턴 0건, 옛 이메일 0건, 사업 용어 0건,
작성자 단일 noreply 를 확인하고 전환했다.

    gh repo edit --visibility public --accept-visibility-change-consequences
    gh api -X POST repos/.../pages -f build_type=workflow

**Pages 설정은 웹 UI 없이 API 로 됐다.** 활성화와 소스 지정이 한 번에 처리된다.

라이브 검증 — `index.html` HTTP 200(280,569 B), `data.js` HTTP 200(477,001 B),
수집일 **2026-08-12**. 라이브 `index.html` 의 `?v=4a14749a` 와 라이브 `data.js` 의
sha256 앞 8자가 일치하고, 로컬 파일과도 sha256 전체가 같다. **화면과 데이터가
어긋난 조합이 올라간 게 아니다.**

`freshness.yml` 도 라이브를 읽고 통과했다 — "수집일 2026-08-12, 1일 경과(상한 10일)".

공개 전환으로 얻은 것: Actions 사용량 무제한, 브랜치 보호·ruleset 사용 가능,
Draft PR 제약 해소.

### 4-6. 브랜치 보호 (완료)

ruleset `main 보호` — `~DEFAULT_BRANCH` 대상, `enforcement: active`.

| 규칙 | 값 |
|---|---|
| Require a pull request before merging | 켜기, **required approvals = 0** |
| Block force pushes (`non_fast_forward`) | 켜기 |
| Restrict deletions (`deletion`) | 켜기 |
| Required status checks | **걸지 않음** |
| Bypass actors | Repository admin (`actor_id: 5`), `bypass_mode: always` |

**승인을 요구하지 않는 것이 핵심이다.** GitHub 문서에 "Pull request authors cannot
approve their own pull requests" 라고 명시돼 있다. 1인 저장소에서 승인을 1건이라도
요구하면 본인 PR 을 본인이 승인할 수 없어 영원히 병합하지 못한다. 유일한 탈출구가
봇 승인인데 그게 곧 자가 승인 구멍이다. **요구 승인이 0이면 봇이 승인해도 얻는 게
없으므로 구멍의 전제가 사라진다.**

**required status checks 를 걸지 않은 이유** — `verify.yml` 은 `paths` 필터가 있어
문서만 바뀐 PR 에서는 아예 실행되지 않는다. required 로 걸면 그런 PR 이 "대기 중"에서
영원히 멈춘다. **조건부 실행 워크플로는 required 로 걸지 않는다.**

이 보호가 실제로 막는 것 — 에이전트가 `main` 에 직접 push 하는 것, force push,
`main` 삭제. bypass 에 관리자가 있으므로 로컬에서 `main` 직접 push 는 그대로 된다.

되돌리려면:

    gh api -X DELETE repos/byoneself4023-bit/seoul-property-dashboard/rulesets/20787745
